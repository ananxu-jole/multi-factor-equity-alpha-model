# Candidate Consolidation Workplan v1

Date: 2026-06-17

## SECTION 1 – Consolidation Objective

Project Underdog must consolidate its current candidate library before launching any new discovery because the active research set is narrow, concentrated, and still dominated by conditional/watch-monitor evidence. Consolidation is needed to:

- prevent redundancy from being mistaken for diversification,
- reduce false-discovery risk by pruning weak variants and diagnostic-only candidates,
- stabilize the inventory around a small, auditable set of repeatable hypotheses,
- preserve the integrity of the current conditional research path while metadata and ML remain immature,
- ensure that the next discovery phase is built on a clean, evidence-backed library instead of a crowded provisional pool.

Consolidation is not a discovery campaign. It is a library-truthing cycle that should expose overlap, confirm or reject candidates in place, and document a stable set of research-ready and reference-only assets.

## SECTION 4 – Evidence Gaps

1. Overlap / correlation testing
- Need a direct correlation and co-activation comparison across the current active candidates, especially the participation/breadth and volatility/stress clusters.

2. Turnover comparison
- Need side-by-side turnover proxy and rank-churn metrics to confirm whether apparent differences are real or driven by the same underlying activation behavior.

3. Active coverage comparison
- Need consistent active-coverage and activation transition review for all candidates to understand exposure depth and sparsity risk.

4. Horizon stability
- Need horizon stability analysis for h10/h15/h20 across all candidates, not just best-horizon snapshots.

5. Watch-monitor refresh
- Need a fresh watch-monitor diagnostic to confirm whether `WATCH_MONITOR` reasons are transient or persistent.

6. State orthogonality / activation overlap
- Need evidence that candidate state definitions are semantically distinct, especially across hostile trend, weak breadth, liquidity repair, and volatility stress states.

7. Peer-relative robustness
- Need a clear plan for eventual peer-relative or sector-neutral testing once point-in-time metadata is available; for now, document the gap.

8. Rebuild / equivalence validation
- Need an exact rebuild/equivalence test for the fixed four-variant package of `participation_liquidity_state_shift_20_60` before treating it as a stable anchor.

9. Out-of-sample drift review
- Need evidence on whether the current candidate behaviors hold across different sample periods and whether recent-window metrics are consistent with longer history.

10. Metadata boundary confirmation
- Need to confirm the limits of static-snapshot metadata so that consolidation is not contaminated by premature peer/sector conditioning.

11. Parked-family boundary confirmation
- Need to ensure the OHLCV Non-Hostile Transition and Leadership Rotation family remains parked as `FAMILY_PARKED_INVERSION_DIAGNOSTIC_OPTIONAL`; no candidate should enter refinement from the negative IC cycle.

12. VoV bounded-refinement boundary confirmation
- Need to ensure only `vov_03_ref_strict_chop` and `vov_01_ref_smoothed_calm` enter validation-design review; `vov_01_ref_anchor` and `vov_03_ref_anchor` remain baseline comparators, `vov_01_ref_longer_memory` remains watch-only, and all original/refinement parked variants remain archived.

13. Dispersion Path-Dependence boundary confirmation
- Need to ensure the Dispersion Path-Dependence module remains parked as `MODULE_GOVERNANCE_PARKED`; `dpath_01` and `dpath_03` remain parked historical evidence, `dpath_02` and `dpath_04` remain unsupported, and no second refinement cycle or new DPath candidate batch is introduced without a new independent Platform v2 hypothesis.

- Required inputs: frozen variant definitions, existing research panels, current metrics table, rebuild code paths, and any prior equivalence review notes.
- Expected output artifact: `artifacts/research/candidate_consolidation/rebuild_equivalence_participation_liquidity_2026-06-17.csv` and a summary note.
- Decision rule: if the rebuilt package matches prior h20 IC, turnover, active coverage, and state semantics within tolerance, keep as core anchor; otherwise downgrade to watch-monitor review and require redesign.
- Candidate group affected: `participation_liquidity_state_shift_20_60`.

### Test 2: Participation / breadth overlap and correlation audit
- Purpose: determine whether `participation_breadth_repair_under_hostile_trend` is a distinct hypothesis or a high-overlap variant of the existing participation candidate.
- Required inputs: candidate signal panels, co-activation matrix, correlation matrix, state slice definitions, and co-activation drift history.
- Expected output artifact: `artifacts/research/candidate_consolidation/participation_breadth_overlap_audit_2026-06-17.csv` and a decision summary.
- Decision rule: if correlation/co-activation remain low and state activation is distinct, retain both; if correlation/co-activation are high and state semantics overlap, reclassify the weaker candidate to diagnostic-only or archive.
- Candidate group affected: `participation_liquidity_state_shift_20_60`, `participation_breadth_repair_under_hostile_trend`, `nonprice_liquidity_persistence_20_60`.

### Test 3: Watch-monitor risk refresh
- Purpose: verify whether the existing `WATCH_MONITOR` candidates still carry the same watch reasons and whether risk status is stable.
- Required inputs: latest rolling/recent-window metrics, one-window dominance and positive-rate thresholds, guardrail failure logs, and candidate signal history.
- Expected output artifact: `artifacts/research/candidate_consolidation/watch_monitor_refresh_2026-06-17.csv` with pass/fail annotations.
- Decision rule: if a candidate continues to fail the same watch reasons, retain monitor status and do not advance; if the watch reasons resolve, re-evaluate for healthy active research or archive.
- Candidate group affected: `participation_liquidity_state_shift_20_60`, `volatility_compression_after_stress_stabilization`.

### Test 4: Coverage / turnover / horizon stress comparison
- Purpose: compare the current candidate library on coverage depth, turnover profile, and horizon stability to identify the strongest library subset.
- Required inputs: candidate metrics tables, coverage ratios, turnover proxies, horizon IC curves, and WFV-style diagnostics.
- Expected output artifact: `artifacts/research/candidate_consolidation/coverage_turnover_horizon_comparison_2026-06-17.csv` and a selection memo.
- Decision rule: if a candidate has materially weaker coverage, higher turnover, and less stable horizon performance than the library anchor, move it to diagnostic-only or archive; otherwise retain it for refinement.
- Candidate group affected: all current active and watch-monitor candidates.

### Test 5: Diagnostic reference curation
- Purpose: decide which rejected or redesign candidates should remain as historical diagnostic references and which should be archived entirely.
- Required inputs: candidate failure notes, structural hypothesis descriptions, rejection reasons, and prior research artifacts.
- Expected output artifact: `artifacts/research/candidate_consolidation/diagnostic_reference_inventory_2026-06-17.csv` and a curation note.
- Decision rule: keep only candidates that provide distinct failure-mode lessons or state-path references; archive those whose only value is historical noise.
- Candidate group affected: `stress_to_normalization_participation_repair`, `conditional_low_overextension_breakout_20`, `gap_followthrough_low_churn_10`, the OHLCV Non-Hostile Transition and Leadership Rotation rejected set, and earlier v2/v3 watchlist names.

### Test 6: Static metadata boundary confirmation
- Purpose: ensure consolidation does not drift into premature peer-relative or sector-conditioned research.
- Required inputs: metadata readiness notes, static-snapshot coverage tables, peer-group thresholds, and current guidance documents.
- Expected output artifact: `artifacts/research/candidate_consolidation/metadata_boundary_confirmation_2026-06-17.md`.
- Decision rule: maintain static-snapshot-only status for all candidate documentation until a separate point-in-time metadata readiness milestone is complete.
- Candidate group affected: all candidates, implicitly.

## SECTION 6 – Governance Guardrails

During consolidation, the following must not change:

- no new discovery
- no new candidate generation
- no candidate promotion without explicit evidence from consolidation tests
- no threshold changes or gate/schema changes
- no production registration or survivor/watchlist state mutation
- no ML modeling or ML-driven decision-making
- no portfolio construction or weighting changes
- no production Conditional-Alpha wiring
- no premature point-in-time metadata conditioning
- no expansion of candidate scope beyond the current library
- no reinterpretation of historical metrics as new validation evidence
